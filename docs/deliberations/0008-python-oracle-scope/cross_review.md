# Cross-review — DELIB-0008

## Reconciliation status

`human_decision_required`

Both independent positions and reciprocal reviews converge on **Option B: a
permanent selective executable oracle**. Neither side supports a permanent
near-complete Python mirror of the future full engine, and neither supports a
wholesale removal of the Python oracle.

The remaining disagreement is narrow: how broad the retained executable
scenario/log-differential harness should remain, and how strongly the repository
should enforce the new opt-in oracle policy.

## Agreed conclusions

1. The current Python oracle is a near-complete second tactical engine, not merely a
   collection of small reference calculators.
2. Automatic full mirroring does not scale to campaign, economy, persistence, AI,
   strategic systems, and deep-mod infrastructure.
3. Python remains permanent where it provides independent compatibility/reference
   value.
4. Independence matters more than language count. A same-session structural port of
   GDScript is weak independent evidence even if it is executable.
5. Recovered exact arithmetic/order, RNG/state topology, legacy parser/import edges,
   compact compatibility decisions, and neutral vector generation remain strong
   candidates for permanent Python reference logic.
6. Project-owned runtime orchestration is GDScript-only by default unless a specific
   compatibility reason justifies Python execution.
7. Existing Python modules are not deleted wholesale. They are classified and
   narrowed incrementally.
8. Campaign/economy/AI/persistence may still contain small recovered kernels that
   justify Python reference implementations; this does not justify mirroring their
   surrounding full subsystems.
9. Future implementation tasks must explicitly state whether Python oracle work is
   required rather than inheriting a parity obligation by habit.
10. Retirement of existing executable coverage must preserve provenance, vectors,
    fixtures, and distinguishing tests.
11. Original-format save compatibility remains a separate product decision.

## Reconciled oracle classes

### O1 — permanent independent reference kernels

Actively maintain small executable Python logic when it satisfies an accepted
retention criterion:

- recovered exact arithmetic/truncation/order;
- RNG/state topology and call-order behavior;
- legacy parser/import semantics;
- compact high-risk compatibility decisions;
- independently grounded neutral vector/fixture generation.

The strongest candidates include legacy RNG and evidence-sensitive numeric kernels.

### O2 — curated executable compatibility integration harness

Retain a live Python end-to-end scenario/log-differential capability because it has
demonstrated value for cross-subsystem sequencing regressions.

However, this is **not** a promise that the current Python tactical engine receives
full feature parity forever.

Policy:

- keep selected compatibility scenarios executable;
- the harness may run new scenarios using semantics already inside its supported
  capability envelope;
- a new production feature does not automatically expand that envelope;
- extend the Python harness only when the feature changes a compatibility-critical
  end-to-end interaction for which focused vectors/local tests are materially weaker;
- prefer a neutral expected trace/vector over generalizing Python orchestration when
  that provides equivalent distinguishing power.

The initial current spine to inventory includes the engine-side candidates:
`scenario.py`, `turn.py`, `battlefield.py`, `combat.py`, `modifier.py`,
`modifier_semantic.py`, `statuses.py`, `auras.py`, and `counterattack.py`.
This list is an **inventory starting point, not permanent module entitlement**.
Retention is capability-based.

### O3 — maintenance-only existing mirror

Existing mirrored project/orchestration modules that do not justify O1/O2 remain
available for current tests/fixtures but stop receiving new feature parity by
default.

Likely initial candidates include content/composition/roster/identity/handler/action
orchestration modules whose Python shape is primarily a structural port.

Maintain only the behavior required by explicitly retained compatibility coverage.
A production bug outside that declared surface does not automatically create a new
Python parity obligation.

### O4 — vectors/specification/research only

Where input/output vectors, properties, or committed traces adequately preserve the
semantic contract, executable mirroring may be retired in a dedicated task.

Historical/research utilities may remain as provenance without becoming parity
obligations.

## Oracle retention criteria

A task may require new/expanded executable Python logic when at least one materially
applies:

1. recovered exact arithmetic/order is compatibility-sensitive;
2. RNG/state/call topology requires independent executable checking;
3. a legacy parser/import edge benefits from independent decoding;
4. a compact high-risk semantic decision kernel benefits from separate derivation;
5. neutral fixture/vector generation needs an independent producer;
6. a compatibility-critical end-to-end interaction has demonstrated or compelling
   sequencing risk that focused vectors cannot distinguish as well;
7. temporary research prototyping is useful, without implying permanent parity.

## Default non-retention criteria

Do not mirror by default:

- generic command/Scenario orchestration outside the declared O2 harness envelope;
- generic mutable state containers;
- campaign/strategic turn orchestration;
- AI planners/controllers;
- economy/progression orchestration;
- EGO-native persistence and migration plumbing;
- UI/presentation;
- package/mod composition architecture;
- plugin/deep-mod hosting infrastructure;
- generic project-owned context/service plumbing.

A small recovered kernel inside one of these systems may still qualify independently.

## Future task-contract rule

Every future implementation task must contain one of:

- `PYTHON_ORACLE: REQUIRED`
  - cite the retention criterion;
  - name the exact Python kernel/module/test surface;
  - state what independent evidence/value it checks.

- `PYTHON_ORACLE: EXISTING_HARNESS_ONLY`
  - production work may require existing curated compatibility scenarios to remain
    green;
  - this does not authorize broadening Python feature scope.

- `PYTHON_ORACLE: NOT_REQUIRED`
  - ordinary project-owned runtime/orchestration or behavior already protected by
    neutral vectors/specification.

Silence is not permission to mirror.

A lightweight mechanical validator should enforce presence/validity of this field for
future CX tasks and flag new/expanded production `oracle/*.py` work without an
explicitly justified oracle scope. The validator must not try to infer whether the
implementation is genuinely independent; that remains a review judgment.

## Retirement discipline

Executable O3 coverage may leave standing-implementation status only in a dedicated
retirement/narrowing task, not incidentally inside unrelated feature work.

That task must:

- identify the exact retained semantic coverage;
- preserve or create committed vectors/traces/properties before retirement;
- preserve provenance of how expected artifacts were obtained;
- prove GDScript is not merely grading output generated from itself;
- update the oracle inventory/classification.

## Fixture clarification

Two distinct authorities must remain clear:

1. reference/generator -> committed expected artifact;
2. GDScript runtime -> committed expected artifact.

A frozen/retired Python generator need not regenerate a fixture forever, but the
fixture must remain traceable to accepted evidence/specification or a retained
historical reference implementation.

## Full-engine application

The decision boundary is semantic, not tactical-versus-strategic.

Examples:

- recovered province-income arithmetic may merit an O1 Python calculator;
- the full campaign-turn engine normally does not;
- recovered recruitment eligibility may merit focused Python vectors/kernel logic;
- the entire strategic content graph does not;
- original-format save parsing could merit an O1 compatibility parser if such
  compatibility becomes a product goal;
- EGO-native persistence architecture remains one production runtime by default.

## Remaining human choices

The positions leave these genuine choices:

1. **Scenario harness breadth**
   - preserve a broad actively evolving Python tactical spine; or
   - adopt the bounded O2 policy above, where new feature parity is opt-in.

   Reconciled recommendation: **bounded O2**.

2. **Mechanical enforcement**
   - rely initially on review discipline; or
   - add a small task-contract/oracle-growth validator before the next major
     subsystem.

   Reconciled recommendation: **add the lightweight guard**.

3. **Retirement rigor**
   - allow opportunistic retirement inside feature tasks; or
   - require dedicated narrowing/retirement tasks.

   Reconciled recommendation: **dedicated task required**.

Original-format persistence compatibility can remain open and does not block this
decision.

## Reconsideration triggers

Reopen this policy if:

- narrowed Python coverage misses concrete compatibility regressions that the former
  live mirror would plausibly have caught;
- systematic evidence shows orchestration differential execution has unusually high
  defect-detection value per maintenance cost;
- automated tooling makes genuinely independent broad mirroring much cheaper;
- EGO intentionally gains a second production runtime;
- a compatibility target requires full-system differential execution that cannot be
  represented adequately by O1/O2 plus vectors.
