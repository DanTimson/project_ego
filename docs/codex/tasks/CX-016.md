## Why this task exists

DELIB-0007 resolved AD-4.

The currently implemented `DeathLifecycle` still owns a universal tier-to-record
mapping and can route replacement through the currently selected pack. That is
unsafe because Genesis records `21/37/56/65` are Genesis source identities, not
pack-independent canonical unit ids.

The accepted architecture is:

```text
rules profile + content compatibility contract
        -> dedicated death-replacement resolver
        -> qualified source record
        -> canonical resolved content definition
        -> generic DeathLifecycle replacement branch
```

Generic `DeathLifecycle` must not own universal raw source ids.

## Goal

Implement DELIB-0007 so that strict Genesis death replacement is active only when:

1. the active rules profile is Genesis; and
2. loaded content is Genesis-compatible under an explicit or inherited
   compatibility contract.

The dedicated resolver owns:
- Genesis applicability;
- the fixed tier->source-record mapping;
- source-record qualification;
- conversion through the selected content provider into a canonical resolved
  replacement definition;
- load-time validation and diagnostics.

Generic `DeathLifecycle` owns lifecycle ordering and replacement application, but
does not know `21/37/56/65`, arbitrary pack ids, or Genesis compatibility policy.

## Content compatibility model

Exact class/field names are implementation-owned, but the semantic distinction is
not.

### Required behavior

A content source has a compatibility identity/contract separate from its arbitrary
pack id.

At minimum support:

```text
genesis-compatible
new-horizons-compatible
project/native/unspecified
```

or an equivalent representation.

The compatibility contract may be inherited from the loader/profile for legacy
stock-derived content.

Requirements:

1. Stock Genesis content is Genesis-compatible by default through its existing
   legacy/profile loading path.
2. A legacy Genesis `.var` / supported `.dat` data mod inherits Genesis
   compatibility automatically; editing data must not require an EGO-specific
   manifest merely to remain compatible.
3. A pack with an arbitrary/custom pack id may be Genesis-compatible if the
   content-loading/composition contract explicitly says so.
4. Pack id string equality alone is not compatibility authority.
5. File hash/byte identity with stock Genesis is not compatibility authority.
6. An arbitrary non-Genesis-compatible pack that happens to contain records
   `21/37/56/65` does not gain Genesis replacement semantics.
7. NH-compatible content does not prove NH replacement semantics.
8. Genesis-compatible content used under native/non-Genesis rules is legitimate;
   the Genesis replacement rule is simply inactive.

Do not require a new manifest for ordinary legacy Genesis data edits if the current
loader can inherit the stock compatibility profile.

## Explicit compatibility override

Content packs and rules profiles are independent dimensions. Unusual combinations
may be explicitly overridden.

Provide one explicit load/composition-root override by which a user may assert that
the selected content should be treated as Genesis-compatible for this load.

Exact schema name is implementation-owned.

Requirements:

- override is explicit, never inferred from numeric records;
- override does not change the tier mapping;
- override does not claim NH rules semantics;
- using the override is represented in diagnostics/normalized composition state
  sufficiently for tests and debugging;
- generic `DeathLifecycle` never reads the override.

A Genesis-compatible declaration/override is an interoperability assertion by the
content/load layer, not binary evidence.

## Strict/default validation

When Genesis rules are active and content is Genesis-compatible:

- validate all four required source targets `21/37/56/65` during
  load/composition/Scenario construction;
- each must resolve through the selected provider to a canonical definition;
- validation must not interpolate the victim's arbitrary pack identity;
- missing/malformed/unresolvable required target is a durable diagnostic;
- strict/default mode fails closed before battle commands can run.

Validation is against content availability/identity, not stock-byte equality.
Definitions at those records may be modified.

If Genesis rules are active but content is not Genesis-compatible:
- do not silently use equal-number records;
- treat the configuration as a compatibility mismatch;
- strict/default construction fails closed unless an explicit compatibility
  override is supplied.

If Genesis rules are not active:
- the Genesis replacement rule is absent/inapplicable;
- no missing-Genesis-target error is required merely because content is
  non-Genesis-compatible or Genesis-compatible.

## Permissive/incomplete-content mode

Provide one explicit load-level permissive/incomplete-content mode consistent with
existing project conventions.

When Genesis rules are active and content compatibility/targets are incomplete:

- load/construct despite durable diagnostics;
- unrelated runtime paths remain usable;
- already-resolvable replacement tiers may still resolve correctly;
- if a fatal event actually reaches an unresolved Genesis replacement path, fail
  explicitly at that path;
- never substitute another pack's same-numbered record;
- never silently disable the applicable Genesis rule.

Do not create per-diagnostic waivers.

The exact mode field may reuse/generalize an existing content-load strictness seam if
architecturally clean, but death replacement must not depend on action composition.

## Dedicated resolver boundary

Introduce a dedicated resolver outside generic `DeathLifecycle`.

Exact names are implementation-owned; a likely shape is one narrow module/class per
language.

The resolver should return a structured outcome sufficient to distinguish:

```text
not_applicable
resolved(canonical definition)
unresolved(diagnostic/error)
```

or equivalent.

It owns profile/content qualification and raw Genesis source records.

Generic `DeathLifecycle` must consume only an already-resolved replacement decision
or callback result.

### Applicability / marker ownership

Preflight must inspect the current replacement marker path.

The final architecture must prevent NH/native Scenario execution from inheriting
Genesis replacement merely because generic death code recognizes the same marker.

Prefer moving Genesis-specific replacement applicability (including any recovered
Genesis marker check needed to enter the branch) behind the dedicated
profile-qualified resolver.

Generic lifecycle may know that a replacement branch exists, but must not itself
assert that raw marker `0x5B` means Genesis replacement in all profiles.

Synthetic unit tests of generic lifecycle may inject a synthetic replacement
decision/callback directly; they must not require the Genesis mapping.

## Canonical content resolution

The dedicated resolver converts a qualified Genesis source record through the
selected content provider into the selected pack's canonical definition.

Positive example:

```text
rules profile: genesis
content pack id: my_balance_mod
content compatibility: genesis
tier: 1

fixed Genesis source record: 21
provider resolves that source record inside my_balance_mod
canonical result: my_balance_mod:unit/21 (or repository-equivalent identity)
definition contents may differ from stock Genesis
```

Negative example:

```text
rules profile: genesis
content pack id: unrelated_pack
content compatibility: native/unspecified
unrelated_pack happens to contain unit/21

result: compatibility mismatch
NOT unrelated_pack:unit/21
```

Do not construct a replacement by taking the victim's current arbitrary pack and
blindly formatting `<pack>:unit/<Genesis number>` without the compatibility gate.
