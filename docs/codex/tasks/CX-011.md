## Frozen implementation rules

### 1. Fatal-damage boundary

Preserve the accepted central damage order already represented by the engine:

```text
account damage channel
remove statuses explicitly flagged remove-on-damage
subtract/cap current life
if current life reaches zero:
    resolve death lifecycle
else:
    continue existing large-hit/morale handling
```

CX-011 must not move remove-on-damage processing to after death resolution.

The death resolver therefore sees the runtime statuses that remain **after**
the existing remove-on-damage step.

If the current low-level damage helper deliberately lacks battlefield context,
do not force scene/scenario dependencies into a pure rules helper merely for
convenience. It may return a fatal result that the authoritative scenario/combat
executor immediately routes through one death resolver with battle context.

There must not be two independent death-resolution implementations or two
resolutions of one fatal event.

Do not change CX-008 damage arithmetic, randomisation, defence, charge, stamina,
morale-attack, or conditional-contribution semantics.

### 2. Death morale happens before survival branches

Once a unit reaches zero life and death resolution begins, perform the accepted
death-morale effects **before** inspecting/acting on revival, rollback,
replacement, or transfer survival branches.

Mandatory normalized coverage:

- each living adjacent ally: morale `-1`;
- each living adjacent opponent: morale `+1`;
- use the existing authoritative morale-adjustment semantics;
- modifier `0x13` immunity must suppress these adjustments exactly as it
  suppresses other covered morale changes.

This means a unit that immediately revives or is replaced has already caused the
adjacent death-morale reaction.

The recovered hero-associated wider allied penalty is mechanically real but its
source selection is expressed through a fixed original tactical-slot subset.
Implement it in CX-011 **only if** the current engine already has an
unambiguous address-free semantic equivalent for that cohort. Do not encode
original slot numbers or invent a new "hero cohort" classification. If no such
equivalent exists, leave this subcase explicitly partial and report it; that does
not block the rest of CX-011.

### 3. Read special lifecycle markers from runtime status state only

At death entry, inspect the live **runtime status/status-owned modifier
collection**, not the generic all-provider effective-modifier sum, for these
special death-time markers:

- `0x49` — remember opposite-side transfer state/payload if represented;
- `0x4A` — full-revival flag;
- `0x5A` — temporary-transformation rollback;
- `0x5B` — replacement flag.

Do not let a numerically equal persistent/intrinsic/aura/environment provider
accidentally activate a runtime death branch.

Synthetic fixtures may create neutral runtime statuses carrying these numeric
markers. That does not implement their missing spell/action producers.

The evidence does not require defining duplicate-special-marker semantics.
Tests may use at most one marker of each special ID. If the current API forces a
choice among multiple `0x49`, `0x5A`, `0x4A`, or `0x5B` instances, stop rather
than inventing precedence beyond the accepted branch precedence below.

### 4. Status clearing and branch order

Death resolution consumes/clears the runtime status collection.

While traversing the pre-clear status state:

1. remember `0x49` transfer state if present;
2. remember whether `0x4A` is present;
3. remember whether `0x5B` is present;
4. apply the `0x5A` rollback semantics below if present;
5. clear the complete runtime status collection.

After that scan/clear:

```text
if 0x4A was present:
    full revival
    then transfer if 0x49 requires it
    return
elif 0x5B was present:
    tier replacement
    then transfer if 0x49 requires it
    return
else:
    ordinary final death
    apply final persistent/battle-owned handling
    apply the accepted final transfer case where representable
```

Thus:

- rollback (`0x5A`) is processed before revival/replacement;
- full revival (`0x4A`) has precedence over replacement (`0x5B`) if both exist;
- no status survives revival, replacement, or final death.

Do not attach automatic duration ticking/expiry to this process. CX-010's R13
boundary remains open.

### 5. Full revival (`0x4A`)

After death morale and status clear/rollback:

- set current life to the **current/restored** effective maximum life;
- clear the morale-break accumulator/current normalized equivalent;
- keep the logical combatant present/alive;
- do not restore or refresh stamina;
- do not restore or refresh ammunition;
- do not restore or refresh morale;
- do not restore or refresh movement/action capacity;
- do not clear or grant `action_spent` / CX-009 activation terminality;
- do not grant a free activation or side phase.

If a `0x5A` rollback also occurred, the revived maximum life must be calculated
from the restored identity, making rollback-before-revival observable.

A transfer marker is applied only after revival state is established.

### 6. Temporary-transformation rollback (`0x5A`)

A death-time rollback restores the combatant's previously saved original/backup
unit identity through a clean Project EGO representation. Do not reproduce
pointer ownership or original `0xA4` record layout.

The rollback itself:

- restores original/backup content/definition identity;
- preserves current tactical position;
- clamps current movement/action capacity **down** to the restored effective
  speed if it is above that maximum;
- clamps current ammunition **down** to the restored effective ammunition
  maximum if it is above that maximum;
- never increases either capacity or ammunition;
- does not itself restore life;
- does not itself restore stamina;
- does not itself restore morale;
- does not itself make a dead unit survive.

Therefore `0x5A` alone on a fatal hit restores identity/clamps resources and
then continues to ordinary final-death handling.

If no clean original/backup identity representation currently exists, introducing
one small address-free battle-state field/snapshot is allowed. Do not clone
arbitrary combatant state or binary layout. The saved state must contain only
what is required to restore the already-accepted temporary transformation
identity semantics.

### 7. Tier replacement (`0x5B`)

The replacement tier is read from the **original/backup unit definition's
tier/rank**, not from the temporary transformed definition and not from the
unit's experience level.

The accepted tier mapping is exact:

```text
tier 1 -> replacement definition ID 21
tier 2 -> replacement definition ID 37
tier 3 -> replacement definition ID 56
tier 4 -> replacement definition ID 65
```

Only tiers 1..4 are authorized in CX-011. The recovered default path does not
provide a safe fallback. If a reachable test/runtime input requires another
tier, **STOP**; do not choose a replacement.

Replacement establishes a new logical persistent unit identity/definition while
preserving the battle position. Preserve persistent formation coordinates too if
the current model already represents them.

After replacement:

- life = replacement effective maximum life;
- stamina = replacement effective maximum stamina;
- ammunition = replacement effective maximum ammunition;
- morale = replacement effective maximum morale;
- morale-break accumulator = 0;
- statuses = empty.

The recovered replacement branch does **not** refresh movement/action capacity
or activation state. Preserve the current capacity and CX-009 `action_spent`
state unless another already-accepted rule in the repository explicitly changes
them. Do not silently call an "initialize unit" helper that grants a fresh turn.

Use existing authoritative effective-max/resource helpers. If one of these
resource maxima does not exist in the current model, do not invent a formula.

If exact replacement IDs are not present in the authored public fallback
content, do not fabricate canonical content records solely to satisfy the test.
Test the exact tier->ID mapping independently and use an existing neutral test
resolver/fixture mechanism for integration. Any new test-only definition must
remain clearly synthetic and must not weaken canonical content-ID rules.

The original executable also writes the new persistent unit back into a
strategy/army slot. If Project EGO's current tactical runtime has no backing
strategy/army object, do **not** create a strategy layer in CX-011. Implement the
battle-facing replacement identity and record strategic writeback as an
intentional remaining boundary. If an existing backing-unit abstraction already
exists, update it through that abstraction without introducing binary slot
layout.

### 8. Ordinary final death and battle-owned state

Ordinary final death must make the combatant non-living and non-actionable and
remove it from **living** battlefield occupancy/targeting.

Preserve enough final positional identity for deterministic trace and a future
corpse system; do not invent corpse-category or terrain presentation rules.

If the current engine already has a tactical-only/battle-owned distinction, use
it. If it lacks one and the distinction is needed to represent the accepted
cleanup, one small normalized boolean/state field is allowed, defaulting to the
persistent case.

For a battle-owned/tactical-only final death:

- the tactical instance is logically discarded/removed from active battle state;
- it must not remain selectable/actionable/occupying;
- no strategy persistence is required;
- do not implement legacy reward/statistic accumulator formulas in this task.

For a persistent final death:

- retain the logical persistent combatant/dead record as the current architecture
  normally does;
- it remains non-living/non-actionable and does not count as living occupancy;
- corpse visuals, corpse eligibility, terrain corpse suppression, resurrection
  target legality, and corpse-eating execution remain future work.

Do not add reward/statistic/XP bookkeeping merely because the legacy death
function also contains it.

### 9. Opposite-side transfer (`0x49` / control transfer)

Implement a clean logical side-transfer primitive:

- exactly one logical combatant survives the transfer operation;
- ownership/side becomes the opposite side;
- the source side no longer contains a duplicate logical unit;
- preserve position and gameplay state except for changes already made by the
  preceding death branch;
- do not refresh resources;
- do not reset `action_spent`;
- do not grant an activation or start/end a side phase.

If the architecture stores units in side-owned arrays, move the same logical
state between sides. If it stores side on the combatant, mutate the authoritative
side identity and ensure all side queries reflect it. Do not emulate the
original full-record copy or UI-pointer preservation.

Death-time ordering:

- revival + transfer: revive first, transfer second;
- replacement + transfer: replace first, transfer second;
- persistent final death + transfer: final dead state may transfer if the
  current normalized model can retain a dead persistent record;
- battle-owned final cleanup does not need a post-cleanup transfer path.

A direct living-unit transfer primitive may be tested separately from the
missing generic action/spell producer.

The numeric/payload meaning carried by a `0x49` status beyond the required
opposite-side transition is not frozen here. Preserve it neutrally if the current
Status model already stores it; do not assign it a game-facing meaning.

### 10. Scheduler, action terminality, and caller boundaries

CX-011 must preserve CX-009/CX-010 boundaries:

- death, revival, replacement, and transfer are lifecycle consequences, not
  implicit side-pass operations;
- revival/replacement do not grant a new activation;
- a transferred unit is eligible only according to its resulting side, life,
  and existing authoritative action-point/terminality state;
- no automatic status-duration tick is attached to death or transfer.

Do not change whole-side phase order.

Do not establish new kill-credit, kill-trigger, reward, R17 secondary-effect, or
retaliation semantics. If an existing executor requires a new explicit choice
for whether a revived/replaced target counts as "killed" for those systems, stop
and report that boundary rather than inventing it.

## Reviewer amendment — ordinary melee fatal-survival sequencing

**Binding clarification:** the existing accepted `EXP-CI11` melee-exchange
listing settles the two ordinary melee continuation decisions that blocked the
first Prime run. No new binary work or evidence-ledger edit is authorized.

### A. Fatal event versus final alive state

Zero life still resolves the death lifecycle immediately. Preserve the semantic
distinction:

```text
fatal_event = this hit reached zero life and invoked death resolution
final_alive = resulting life/alive state after that resolution
```

Use any small clean representation that fits the existing architecture. A fatal
event is not automatically a permanent kill, reward, kill credit, or R17 trigger.

### B. Lethal defender first strike

```text
apply defender first-strike damage
if initiator reaches zero:
    resolve death lifecycle immediately

if initiator is alive / has positive life after resolution:
    execute initiator primary attack
else:
    end exchange without primary
```

Thus `0x4A` revival or `0x5B` replacement that leaves the initiator alive after
a lethal first strike permits the initiating primary attack.

### C. Lethal initiating primary

```text
apply initiating primary damage
if defender reaches zero:
    resolve death lifecycle immediately
    remain on the fatal-event exchange branch
    do not execute ordinary retaliation
else:
    continue through existing ordinary retaliation gates
```

Therefore a defender revived by `0x4A`, or surviving via `0x5B` replacement,
still does not gain ordinary retaliation for the same exchange. Do not simplify
both B and C to one post-resolution `if alive` rule.

### D. Scope

This clarification covers only defender first strike, initiating ordinary
primary, and ordinary retaliation. It does not settle R17 follow-up/cleave/
double/trample/instant-death sequencing, secondary recursion, kill-trigger
actions, kill-credit, rewards, XP/statistics, or generic action producers.

If implementing the ordinary rules forces one of those separate policies, stop
on that separate dependency instead of importing legacy bookkeeping.

   ordinary retaliation;
