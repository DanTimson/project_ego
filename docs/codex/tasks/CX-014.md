## Why this task exists

DELIB-0004 is decided and its first production-composition tranche (AD-3 / CL-1)
is implemented and review-accepted. The accepted product decision requires two
execution tiers:

1. declarative execution plans composed from safe engine primitives for
   data-defined actions;
2. a later trusted extension/plugin recipe API for behavior outside that
   declarative primitive set.

CX-014 implements only tier 1, version 1.

The existing boundary remains authoritative:

```text
pack/source action identity
    -> canonical Action definition
    -> recipe resolution
    -> fresh immutable ActionExecutionPlan
    -> shared tactical primitives
```

CX-014 must extend this boundary, not replace it.

## Goal

Allow a pack-defined, namespaced action to become executable through a validated
declarative recipe that compiles into the existing typed plan model.

The v1 declarative layer must:

1. be data, not executable script;
2. be validated at composition/load time;
3. resolve from canonical Action identity only;
4. produce a fresh plan per command;
5. reuse the existing plan executor and shared primitives;
6. preserve all existing command validation/payment/terminality behavior;
7. preserve built-in Crushing Blow and Shield Bash semantics exactly;
8. keep malformed/unsupported declarative recipes explicit and fail-closed by
   default;
9. remain pack/profile isolated;
10. introduce no new gameplay primitive kind.

## Declarative recipe ownership

A declarative recipe is canonical action-definition metadata for a pack-defined
action. Exact schema key names/classes are implementation-owned.

Requirements:

- raw source ids and localized display names are never recipe dispatch keys;
- recipe metadata follows the already-resolved canonical action definition;
- a per-unit grant may override only the existing explicitly allowed action fields;
  it must not rewrite the recipe;
- resolving a grant must not mutate the shared recipe definition;
- a recipe must not be stored as mutable runtime state on a Combatant;
- plan compilation must deep-copy/freeze any mutable recipe input needed by the
  fresh plan.

### Shared engine-known identities

Declarative pack data must **not** override the engine-owned recipes of:

- `crushing_blow`;
- `shield_bash`.

If an overlay attempts to attach/replace declarative recipe semantics on one of
those shared canonical identities:

- strict mode fails closed with a specific diagnostic;
- permissive mode retains a diagnostic and the existing engine-owned recipe
  remains authoritative.

Do not create a content path that silently changes accepted Genesis-compatible
behavior while retaining the shared canonical identity.

## V1 safe operation subset

CX-014 may compile only the operation kinds already implemented by CX-013.

### Declarative melee AttackOp

Allowed shape:

```text
kind = attack
mode = melee
selected target = existing command target
initiating attack scale = literal exact positive rational
```

Rules:

- only melee is supported in v1;
- numerator and denominator are positive integers;
- denominator is nonzero;
- scaling uses the existing exact integer/trunc0 path;
- no counterattack/first-strike suppression flag;
- no charge override;
- no defence/RNG/death override;
- no free-form modifier map;
- no raw legacy opcode;
- no display-name dispatch.

The result must be the same typed `AttackOp` already used by Crushing Blow.

### Declarative stamina ResourceDeltaOp

Allowed shape:

```text
kind = resource_delta
target = selected enemy
resource = stamina
amount = one of:
    fixed non-positive integer
    negative resolved action magnitude
```

Rules:

- selected target only;
- stamina only;
- v1 is drain-only: amount must never be positive;
- if sourced from action magnitude, the resolved per-unit action magnitude is used;
- existing effective-0x12 tactical stamina-write suppression remains authoritative;
- floor-zero behavior remains the existing shared primitive behavior;
- no generic resource setter/interceptor is introduced.

The result must be the same typed `ResourceDeltaOp` already used by Shield Bash.

## Ordered-plan restriction for v1

The declarative recipe may contain an ordered operation list, but CX-014 must avoid
inventing post-damage/fatality/event semantics.

Therefore v1 permits:

- zero or more stamina `ResourceDeltaOp`s;
- at most one melee `AttackOp`;
- if present, the `AttackOp` must be the **final** operation.

Reject:

- more than one AttackOp;
- any operation after AttackOp;
- empty operation list;
- unknown operation kind.

Do not add transactional rollback. All declarative structure and static parameters
must be validated before command payment.

## Recipe resolution

Preserve existing built-in resolution:

```text
crushing_blow -> engine recipe -> plan
shield_bash   -> engine recipe -> plan
```

For a pack-namespaced action:

```text
canonical Action + valid declarative recipe
    -> compile recipe
    -> fresh ActionExecutionPlan
```

A valid pack action with no declarative recipe remains known but unsupported exactly
as before.

A malformed declarative recipe:

- strict load: composition/load fails closed;
- permissive load: definition remains diagnosable, unrelated content remains usable,
  and invoking the affected action refuses explicitly as an unresolved/invalid
  recipe;
- it must never fall back to a built-in recipe by name/source id;
- it must never partially compile or execute.

Use the existing diagnostic architecture where practical.

## Compatibility/profile boundary

Declarative recipes are project-authored mod behavior, not recovered Genesis/NH
semantics.

Therefore:

- adding a new namespaced recipe to a Genesis/NH data mod is allowed;
- this does not make the action a recovered stock action;
- the stock two shared recipes remain engine-owned;
- do not attach declarative recipes to the other twelve reference actions merely
  because their names/effect fields are known;
- do not claim New Horizons rules compatibility from declarative recipes.

Two packs with the same local source/action id must retain distinct namespaced recipe
identity and cannot see each other's recipe metadata.

## Command semantics

Do not redesign `Scenario.cmd_action` / `_resolve_action_command`.

All existing ordering remains:

```text
canonical action lookup
recipe support/refusal
actor availability
target legality
payment exactly once
execute fresh typed plan
CX-009 terminality
```

Declarative recipes must obey the same target/payment/refusal boundary as built-in
recipes. All pre-execution refusal cases are mutation-free.
