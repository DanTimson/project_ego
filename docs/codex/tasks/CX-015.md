## Why this task exists

DELIB-0006 resolved AD-2. A single generic `prevents_action`/`can_act` authority is
not the accepted architecture.

The accepted capability model distinguishes at least:

- movement;
- ordinary melee;
- ordinary ranged attack;
- casting;
- activated actions.

A fully disabling state is represented by the composition of the relevant typed
restrictions, not by a universal action flag.

CX-015 implements that architecture at the current tactical model/query/command
boundary.

## Goal

Replace generic action prevention with one typed restriction authority that answers
capability-specific questions without conflating unrelated actions.

Address-free semantic rule:

```text
a unit may perform capability C
    iff no effective status/effect on that unit restricts capability C
    and all other existing command-specific legality checks pass
```

Restrictions are independent. For example:

- movement restriction alone does not block ordinary melee, ranged, casting, or
  activated actions;
- melee restriction alone does not block movement or activated actions;
- activated-action restriction alone does not block ordinary melee;
- a fully disabling state is the union/composition of all required restrictions.

Do not infer that executing an `AttackOp` inside an activated action turns that
command into an ordinary-melee command. Capability authority is consumed at the
command/query surface, before primitive execution.

## Storage model

Exact storage representation is implementation-owned.

Acceptable implementations include a closed set/bitset/enum-backed collection or
equivalent typed fields. The production API must nevertheless expose the five
semantic capabilities unambiguously:

```text
movement
melee
ranged
casting
activated_action
```

Requirements:

1. no display/localized string is semantic authority;
2. unknown capability values fail closed at content/model validation boundaries
   according to existing strictness conventions;
3. copying/serialization of Status/StatusEffect data preserves restrictions without
   mutable aliasing;
4. restrictions compose by union across simultaneous effective statuses/effects;
5. duplicate restriction declarations are idempotent;
6. removing/expiring one status removes only the restrictions contributed by that
   status; another active status can continue to block the same capability;
7. restriction state is not cached globally on Combatant unless existing status
   lifecycle invalidation makes that cache provably correct. Prefer query-on-demand.

Do not create a battle-global permission registry.

`Status.prevents_action` is not authoritative.

For CX-015:

  compatibility consumer exists;
- remove generic `Statuses.can_act` / `oracle.statuses.can_act` authority;
- remove or rewrite fixtures/tests that canonize generic `can_act`;

If an obsolete input key `prevents_action` must remain parseable for a project-owned
fixture or migration reason, it must have **no semantic authority** and the reason
must be documented. Prefer deleting the obsolete project-authored surface.

## Query API

Provide one authoritative typed capability query in each language, either:

```text
Statuses.can_<capability>(unit)
```

or:

```text
Statuses.can_perform(unit, capability)
```

or an equivalently explicit typed API.

Return/refusal shape should follow existing repository conventions. It must identify
the blocking status/effect sufficiently for diagnostics/tests without exposing
binary addresses or research-only identifiers.

Do not route one capability query through another capability's result.

## Command/query integration

### Movement

`ActionPoints.can_move` / `oracle.turn.can_move` must consume the movement
restriction in addition to their existing action-spent, capacity, path, and movement
rules.

Preserve existing refusal precedence unless the base architecture clearly requires
the typed restriction to be checked earlier. Record the actual precedence in tests.

### Ordinary melee

Wire the existing ordinary-melee command/query surface, if present, to the melee
restriction.

A melee restriction blocks the ordinary initiating melee command before payment,
RNG, attack execution, retaliation, or terminality mutation.

It does not by itself block `cmd_action`.

### Ordinary ranged

Wire the existing ordinary-ranged command/query surface, if present, to the ranged
restriction.

A ranged restriction blocks before ammunition/stamina/payment, RNG, damage, or
terminality mutation.

Do not implement ranged combat features that do not already exist.

### Casting

If a production casting command/query surface already exists, wire it to the casting
restriction.

If no such surface exists at this base:
- implement and test the typed casting capability query only;
- document the command integration point as future work;
- do **not** invent a spell/casting command system for CX-015.

### Activated actions

`Scenario.cmd_action` / Python equivalent must consume the activated-action
restriction before payment and plan execution.

This applies equally to:
- built-in Crushing Blow;
- built-in Shield Bash;
- CX-014 declarative pack actions.

A melee restriction by itself must not block an activated action merely because the
compiled plan contains a melee `AttackOp`.

Likewise an activated-action restriction does not by itself block ordinary melee.

## Required distinguishing coverage

Matching Python/GDScript coverage is required.

### A. Independence matrix

For each single capability restriction on an otherwise eligible unit, prove:

1. movement restriction blocks movement query/command only;
2. melee restriction blocks ordinary melee only;
3. ranged restriction blocks ordinary ranged only;
4. casting restriction blocks casting query/command only;
5. activated-action restriction blocks `cmd_action` only.

Where a production command does not exist (especially casting), prove the query
matrix without inventing that command.

At minimum explicitly distinguish:

- melee blocked + activated action allowed;
- activated action blocked + ordinary melee allowed;
- movement blocked + melee allowed;
- ranged blocked + movement allowed.

### B. Full disable by composition

6. one status/effect carrying all five restrictions blocks all five capability
   queries;
7. equivalent restrictions split across multiple simultaneous statuses compose to
   the same effective result;
8. removing one contributor restores only capabilities no longer blocked by another
   active contributor.

### C. Multiple contributors / lifecycle

9. two statuses both blocking melee remain blocking after only one is removed;
10. expiration/removal uses the existing status lifecycle and does not leave stale
    restriction state;
11. duplicate capability entries on one status are idempotent.

Do not implement unresolved R13 lifecycle semantics; use only lifecycle behavior
already accepted by CX-010.

### D. Mutation-free refusal

For every integrated command surface:
12. a restriction refusal occurs before payment/resource change;
13. before RNG use;
14. before damage/status mutation;
15. before action terminality mutation.

Use before/after state assertions and deterministic RNG probes where the existing
test harness supports them.

### E. Activated action boundary

16. activated-action restriction blocks Crushing Blow before payment/execution;
17. activated-action restriction blocks Shield Bash before payment/execution;
18. activated-action restriction blocks a CX-014 declarative pack action;
19. melee restriction alone does **not** block Crushing Blow or a declarative
    activated action containing an `AttackOp`;
20. activated-action restriction alone does **not** block ordinary melee.

### F. Generic authority removal

21. production `Status`/`StatusEffect` no longer has authoritative
    `prevents_action`;
22. production generic `can_act` authority is absent;
23. fixtures no longer use generic `can_act` as semantic truth;
24. no replacement universal action-prevention boolean is introduced.

### G. Existing behavior preservation

25. unrestricted movement behavior remains unchanged;
26. unrestricted ordinary melee/ranged behavior remains unchanged;
27. unrestricted activated actions preserve CX-013/CX-014 behavior;
28. status stacking/refresh/removal behavior outside capability restriction is
    unchanged;
29. no AD-1 modifier-7 or AD-4 death-replacement behavior is added.
