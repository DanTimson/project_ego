## Accepted defect A — invalid aura construction can publish a usable Scenario

Current GDScript flow can:

1. construct battlefield/sides successfully;
2. enter `_build_auras`;
3. encounter an invalid aura modifier (for example an unknown semantic key);
4. set `construction_error` and return an empty aura map;
5. finish `Scenario._init()` without invalidating the otherwise usable Scenario;
6. allow `ManualBattleSession.begin()` and the tactical controller to start it.

This is the same fail-open construction class previously closed for duplicate inline
IDs/failed placements by IR-1.

### Required behavior

A Scenario with any aura-construction error must not become a playable battle.

At minimum:

- `_build_auras` failure remains diagnostic and deterministic;
- `Scenario._init()` must detect the failure after aura construction;
- the invalid Scenario must be unmistakably unusable by ordinary battle execution;
- `ManualBattleSession.begin()` must reject a Scenario whose construction failed;
- the production tactical restart/load path must not silently continue into a
  playable battle;
- no already-built field/unit state may accidentally make the invalid Scenario look
  valid to callers.

Reuse the established IR-1 construction-failure pattern where appropriate rather
than inventing a second lifecycle.

Do not make malformed auras silently disappear.

## Accepted defect B — unresolved fatal replacement can leave phantom living state

Current fatal-event flow can reach a replacement decision with status `unresolved`
(for example a Genesis replacement-bearing unit whose tier is outside the fixed
1..4 mapping).

Before inspecting that status, `DeathLifecycle.resolve()` may already:

- modify adjacent morale;
- restore rollback definition state;
- clear statuses.

The unresolved result is then returned.

`Damage.apply_received_damage()` discards the resolver return value, recomputes the
unit as finally dead from `life <= 0`, and the Scenario can remove battlefield
occupancy while the unit still has `alive == true`.

`RoundLoop.Side.living()` uses `alive`, so the engine can then disagree about
whether the off-board unit is alive.

Python currently fails loudly on the analogous unresolved status; GDScript can
silently continue.

### Required invariants

After CX-018, no accepted or errored fatal-event path may leave:

```text
unit.alive == true && unit.life <= 0
```

as a reachable post-command battle state.

Battlefield occupancy, side living queries, activation/selectability, and the unit's
life/alive state must agree.

An unresolved replacement must not be silently treated as successful replacement.

### Lifecycle preflight requirement

Validate the replacement decision/status before lifecycle-only mutations whose
meaning assumes that fatal resolution can complete.

For an unresolved/error replacement decision, do not first:

- mutate adjacent morale;
- apply rollback-definition restoration;
- clear statuses.

Preserve the successful-path ordering exactly.

This is a preflight of the already-computed decision, not a redesign of the lifecycle
semantics.

### Error propagation requirement

Do not discard the death resolver's failure result.

Implement the narrowest existing-style propagation/fail-closed mechanism that
satisfies all of these:

1. the caller can observe that fatal resolution failed;
2. the unit cannot remain a phantom living/off-board combatant;
3. occupancy and side-living state remain coherent;
4. successful revive/rollback/replacement/final-death behavior remains unchanged;
5. ordinary accepted attack ordering, payment, RNG, and trace behavior remains
   unchanged when no lifecycle error occurs.

A broad transaction/rollback framework is explicitly out of scope.

Do not convert an unresolved replacement into an invented replacement semantic.

If the current command-result surface cannot represent the error cleanly without a
large architecture change, use a narrow explicit runtime-error field/diagnostic and
a coherent fail-closed battle state, and document the residual larger result-contract
question for the later APA-001/APA-006 deliberation.

## Strict versus permissive behavior

Preserve the accepted CX-016 distinction:

- strict Genesis-compatible construction validates the four fixed replacement
  targets up front;
- permissive mode may defer unresolved compatibility failures until the rule is
  exercised;
- when such a deferred failure is exercised, it must fail visibly and coherently,
  not silently corrupt state.

Do not expand strict construction into speculative validation of every future
transformation/content possibility unless necessary to close the concrete tier-range
case cleanly.

A tier outside the evidence-backed 1..4 replacement map remains unresolved. Do not
invent a fifth mapping or fallback target.

## GDScript/Python parity

and distinguishing tests.

on:

- unresolved replacement is not success;
- lifecycle-only mutations do not occur before unresolved-decision rejection;
- no successful return exposes contradictory living/dead state;
- valid fatal-event paths retain existing behavior.

Do not broaden the Python oracle during this task.
