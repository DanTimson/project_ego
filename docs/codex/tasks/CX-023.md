## Goal

The default fallback demo's Azure Ranger starts with Tangled Bowstring.
It blocks only RANGED via the existing typed Status restriction. The Ranger
can move into range during the opening Azure phase but cannot shoot.
After that phase ends, the Ranger can shoot when Azure is next active.
The UI identifies the cause and expiry, and the event log records expiry.

## Native semantics

Provide a narrow Scenario-owned setup seam for an opening restriction,
called before the first battle phase. Use the existing Status and
Statuses capability gate. Opening restrictions apply to a specific battle
instance and expire when its side at setup completes its first phase.
That includes an explicit pass and an automatic exhaustion transition.
The other side ending a phase, selection, queries, and ordinary actions
do not expire it. Expire at the outgoing-side boundary, before entering
the next phase or running any new-round refresh/upkeep. A unit that changes
sides still uses the original side's boundary.

Track the exact installed Status instance in that Scenario. If death
lifecycle or an explicit removal already cleared it, drop the tracking
entry without an expiry event. Never erase an unrelated status with the
same ID. An expiry removes just the tracked restriction and emits one
readable event. Ordinary statuses and their durations keep their existing
behavior. The setup seam applies only to a valid native battle before its
first phase. Keep any setup refusal clear and mutation-free.

Use the existing fallback demo setup seam to apply Tangled Bowstring only
to azure-ranger-17. Keep the standalone fallback JSON independently
runnable. The UI displays the restriction and its expiry, and pressing
Ranged while restricted gives the cause rather than a generic range/ammo
message. Read restriction state from the engine; legality remains with
the command gate. Keep the Vanguard and Stamina Drain paths intact.
