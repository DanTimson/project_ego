### B. Accepted-source conflict is resolved: current oracle/core are stale

The first preflight found that the stable oracle and GDScript currently always
select ranged defence. That is a real implementation divergence, not an
unresolved semantic choice.

The accepted recovered complete body of the ranged damage calculator is binding
for this task. Correct the Python oracle and GDScript to this normalized
address-free rule:

```text
attack_power = effective ranged attack

if effective attacker modifier 0x1C != 0:
    defence_input =
        effective target resistance
        - effective attacker modifier 0x5F

    damage = resolve attack_power against defence_input
    received_damage_channel = 2

else:
    defence_input = effective target ranged defence

    if effective attacker modifier 0x11 != 0:
        defence_input = trunc0(defence_input / 2)

    defence_input -= effective attacker modifier 0x4D

    damage = resolve attack_power against defence_input

    modifier_0x3C = effective attacker modifier 0x3C
    target_resistance = effective target resistance
    if target_resistance < modifier_0x3C:
        damage += modifier_0x3C - target_resistance

    received_damage_channel = 1
```

`trunc0` means signed integer division toward zero. Reuse the repository's
already-accepted signed integer semantics; do not replace it with floor division
for negative odd values.

Important branch consequences:

- `0x1C` chooses the resistance branch **and** channel 2;
- `0x5F` subtracts from resistance only on that branch;
- the `0x1C` branch returns directly after the ordinary resolver and therefore
  does not execute the `0x11`, `0x4D`, or `0x3C` non-resistance tail;
- without `0x1C`, `0x11` halves ranged defence before `0x4D` is subtracted;
- `0x3C` is a post-resolver adjustment only on the non-`0x1C` path, adding the
  positive excess `modifier_0x3C - target_resistance` when that modifier exceeds
  target resistance.

The current oracle is a permanent reference implementation but is not immune to
correction when a proven accepted source demonstrates a stale implementation.
After CX-012 the corrected oracle and GDScript must agree with the frozen rule
above.

No evidence ledger/map/source-confidence edit is authorized: the accepted
recovered claim already exists.
