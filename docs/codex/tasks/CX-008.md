## Authoritative implementation rules

### R3 — modifier `0x25` charge

For the initiating ordinary melee attack command:

- evaluate charge applicability **before approach movement**, not merely the
  coordinate operands;
- a no-movement attack has zero charge;
- when movement is requested and modifier `0x25` is applicable, compute the
  command-local integer from the attacker and target coordinates that exist
  before approach movement:

  `max(abs(attacker_x - target_x) + abs(attacker_y - target_y) - 2, 0)`

- the current command's movement does not recompute that stored integer;
- earlier movement matters only insofar as it changed the attacker's current
  command-entry tile; cumulative `steps_this_round` is not the source;
- the stored integer belongs only to the initiating attacker's primary ordinary
  melee hit. It does not apply to defender first strike, retaliation, ranged
  attack or spell/action damage;
- consume it only after the ordinary melee damage calculation has produced its
  normal randomized/defended result. It is a flat, unrandomized, undefended
  addition to that initiating hit, before the existing central life-damage
  application. Preserve the accepted existing cap against available life;
- do not feed charge into effective attack, wound/stamina/morale multiplication,
  modifier `0x3D`, attack randomisation or defence.

Do not create a persistent unit stat for this command-local value.

### R6 — zero-entry attack semantics

Do not unify ordinary attack, counterattack and ranged attack zero handling.

- ordinary attack and counterattack may reach the shared final minimum-one tail
  from a zero pre-tail value when effective modifier `0x26` is absent;
- effective modifier `0x26` preserves the offensive-disable zero result;
- ranged attack has the accepted early zero-entry guard: if the accepted
  definition-base + instance + intrinsic entry sum is zero, return zero before
  later providers and before the final minimum-one clamp;
- preserve existing provider order and integer truncation. Do not redesign the
  effective-stat API merely to make the three paths look uniform.

Tests must include the zero boundary for ordinary attack, counterattack and
ranged attack separately.

### R8 — live-capacity stamina-cost discriminator

On the recovered ranged-attack stamina-cost path, choose the base attack stamina
cost from **live current action/movement capacity**, not historical movement:

- current capacity `<` effective speed -> base cost `2`;
- otherwise -> base cost `1`.

The comparison is strict. `steps_this_round`, displacement, command-entry
distance and cumulative path length are not substitutes.

Do not generalize this predicate to another action/executor unless an accepted
repository specification already assigns the same rule there. If an affected
non-ranged path remains semantically unspecified, leave it unchanged and report
that boundary.

### R9 — effective ordinary and ranged defence

For each defence path:

1. aggregate that path's already applicable provider set;
2. if current stamina is **exactly zero**, halve the signed integer using
   truncation toward zero;
3. clamp the final result to a minimum of zero.

Do not add wound or morale multiplication. Do not merge the ordinary-defence and
ranged-defence provider sets merely because their final reduction order matches.

Tests must cover at least:

- positive odd defence at stamina zero;
- negative pre-clamp defence at stamina zero;
- stamina one versus stamina zero;
- ordinary and ranged paths independently.

### R10 — modifier `0x3D` conditional contribution

R10 freezes **numeric stage placement**, not a new target-classification rule.
For an already-applicable modifier `0x3D` contribution:

- start from the finalized effective ordinary attack/counterattack value;
- the contribution is outside wound, stamina and morale multiplication;
- for the accepted selected ordinary-attack 1.5x branch, the contribution is
  added after that branch;
- add the contribution before attack randomisation and defence;
- it is therefore conditional attack, not flat post-resolution damage;
- do not apply it to ranged attack unless an accepted specification explicitly
  says so.

Use an existing accepted applicability/provider boundary. Do **not** infer the
condition from a localized ability name. If the current engine has no
semantically accepted way to determine applicability, stop that part and report
the missing boundary rather than inventing one.

### R11 — effective modifier `0x12` and stamina mutations

Effective modifier `0x12` suppresses the individual recovered tactical stamina
mutations locally.

- guard each currently implemented, evidence-covered tactical stamina mutation
  at the local mutation site;
- do not implement a fictitious global stamina setter/interceptor;
- modifier `0x12` does not restore stamina;
- current stamina still participates in effective-stat penalties, including R9
  zero-stamina defence handling;
- do not add missing tactical subsystems solely to manufacture additional
  `0x12` consumers.

Tests must prove both sides: a covered mutation is suppressed, while an already
low/zero stamina value still affects effective statistics.
