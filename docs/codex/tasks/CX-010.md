## Why this tranche exists

Timed statuses are currently split rather than wholly absent:

- Python/rules-level status behavior and tests already exist;
- `core/rules/statuses.gd` already contains project-authored stacking/resistance
  architecture and is used by the tactical engine;
- status-provided modifiers already participate in effective modifier
  aggregation;
- `core/model/status.gd` is still an empty placeholder;
- the full GDScript runtime-effect container/lifecycle is therefore incomplete.

The public-lineage audit classifies the stacking/resistance architecture as
project-authored/publicly supportable (`N0_PUBLIC`, `T0_RETAIN`) but explicitly
classifies duration tick/expiry and `UNTIL_NEXT_TURN` boundaries as unresolved
exact-edge work pending black-box lifecycle evidence, especially R13.

CX-010 closes the **stable container and manipulation gap**. It must not pretend
to close the unresolved clock/lifecycle boundary.

## Goal

Create a real GDScript `Status` runtime model and integrate it through the live
tactical state so existing stable status semantics are represented by first-class
runtime objects rather than ad-hoc dictionaries/arrays.

The tranche should make stable status behavior executable end to end:

- construct/store status instances;
- expose their modifiers to the existing modifier pipeline;
- preserve the current stable stacking/merge/resistance policy;
- support explicit status removal and explicit duration shortening/manipulation
  already specified by the current oracle/rules layer;
- load and trace synthetic statuses in deterministic scenarios;
- keep Python/GDScript fixtures aligned where the semantics are already stable.

Do **not** choose when a duration automatically ticks or expires in actual battle
time.

## Authority boundary

### Stable and implementation-ready

The following may be implemented from existing project/public specifications and
the already passing Python/rules tests:

- a runtime status instance may own a collection of `Modifier` objects;
- status-provided modifiers participate in effective modifier aggregation;
- stable project-authored stacking/merge policy already expressed by
  `core/rules/statuses.gd` / `oracle/statuses.py`;
- stable resistance/acceptance policy already expressed there;
- explicit removal of status effects;
- explicit shortening/reduction/manipulation of status duration where the caller
  supplies the operation;
- deterministic serialization/trace representation needed by synthetic tests.

Preserve the existing policy rather than redesigning it for elegance.

### Explicitly unresolved and forbidden to freeze

Do **not** establish any of the following as compatibility truth in CX-010:

- whether ordinary numeric duration decrements at round start, owner-side start,
  selection/activation start, activation end, side end, or another clock point;
- whether same-side deselect/reselect consumes a duration tick;
- whether a granted extra turn consumes or refreshes a duration tick;
- exact `UNTIL_NEXT_TURN` expiry boundary;
- exact wake/remove-on-damage point for sleep-like effects;
- exact order between automatic expiry and start-of-turn effects;
- exact original runtime-node memory layout/list organization.

R12/R13 are still observation-first. Their protocol is **not an observation
result**. Empty/uncompleted observation sheets must never become expected values.

If completing the stable container truly requires choosing one of these
boundaries, stop and report the dependency rather than inventing it.

## Frozen implementation rules

### 1. `Status` is a gameplay model, not a recovered binary struct

Implement `core/model/status.gd` as a clean, address-free Project EGO model.

It should contain only fields/operations required by the stable engine
semantics actually used by current status rules and fixtures. Do not reproduce
binary node pointers, original allocation layout, offsets, or list mechanics.

Prefer typed fields and explicit copy/serialization helpers over loose
dictionaries where doing so removes ambiguity without changing semantics.

### 2. Modifier ownership

A live status must expose its modifiers in the same source category currently
used by the engine.

`Damage.effective_modifiers()` (or its current successor after CX-008) must
continue to combine:

1. unit-owned/intrinsic modifiers;
2. status/runtime modifiers;
3. environment/aura modifiers,

while preserving the R6 ranged early-provider separation introduced by CX-008.
Do not accidentally reclassify status modifiers as unit-owned early providers.

A status carrying a numeric attack/defence modifier must therefore affect the
same effective-stat paths that currently consume status modifiers.

### 3. Stable stacking/merge policy

Treat the existing `Statuses`/oracle policy and its passing stable tests as the
semantic contract for:

- whether a newly applied effect is accepted/resisted;
- how effects with the same grouping/identity interact;
- whether modifiers stack, merge, replace, refresh, or remain separate where the
  existing stable tests already distinguish those cases;
- explicit duration-shortening/removal operations.

Do not broaden a test's local policy into a universal Eador rule if the current
code represents per-effect policy.

If a current test concerns automatic battle-time ticking/expiry, classify that
test as lifecycle-boundary material and do not use it to wire an automatic clock.

### 4. Combatant ownership and identity

`Combatant.statuses` must contain real status objects after this tranche.

Status instance identity must remain separate from user-facing/display text.
Use existing content/instance identity abstractions if status definitions already
have them; do not invent canonical content IDs for statuses where the current
content model has no such concept.

Copy/clone/scenario construction must not alias mutable status arrays or
modifier arrays between combatants unintentionally.

### 5. Explicit manipulation is allowed; automatic clock is not

It is valid to provide/test operations such as:

- add/apply a status;
- remove one or more status instances by the existing stable predicate/group;
- shorten a duration by an explicit amount;
- query active modifiers/flags;
- serialize stable status state.

These operations are deterministic because the caller explicitly requests them.

Do not have `RoundLoop`, selection, `begin_round()`, extra-turn refresh, or
CX-009 activation terminality automatically tick/expire statuses in this task.

### 6. Scenario integration

Synthetic scenario input may initialize statuses using an explicit neutral
schema if the repository already has a status fixture/schema to extend.

Scenario final-state/trace output should make stable status state observable:
identity/group where available, remaining explicit duration representation, and
modifier payload sufficient for deterministic fixture comparison.

Do not expose binary addresses or localized inferred ability names as engine
semantics.

Existing scenarios with no statuses must remain behaviorally unchanged.

### 7. Active-action boundary

CX-010 may use existing explicit status application/removal helpers in synthetic
tests, but it does not implement the broad battle-action effect dictionary.

Do not add missing poison/sleep/web/dispel spell executors merely to prove the
container works. `ACTION_SEMANTICS_AUDIT.md` already records several such
families as future consumer work.

A synthetic direct status application path is sufficient for this tranche.

### 8. Profile boundary

Do not create new Genesis/NH/native policy.

Stable project-authored stacking/container behavior may remain profile-neutral
where it already is. Exact lifecycle boundaries remain unresolved rather than
being silently assigned to a profile.

## Required deterministic coverage

Add/expand both Python and GDScript coverage where corresponding semantics exist.

At minimum cover:

1. **construction / isolation**
   - two combatants receive equivalent status definitions;
   - their mutable runtime status/modifier state is not aliased.

2. **numeric modifier reaches live effective stat**
   - apply a synthetic status with a positive numeric modifier;
   - verify live effective attack or defence changes;
   - remove the status and verify the value returns;
   - this must traverse the actual engine provider aggregation, not only a
     status helper.

3. **flag modifier reaches a live consumer**
   - use an already-supported status-carried flag with an existing consumer;
   - verify the consumer sees it through `Combatant.has_flag()` or the current
     equivalent;
   - do not invent a new flag meaning.

4. **stable same-group stacking/merge**
   - at least one existing policy case that distinguishes add/merge/replace or
     refresh behavior;
   - expected result must already exist in the stable oracle/rules tests.

5. **resisted/rejected application**
   - one existing deterministic resistance/acceptance case;
   - rejected application leaves the status collection unchanged.

6. **explicit duration manipulation**
   - explicit shortening/removal produces the already-specified result;
   - no round/selection/extra-turn event is involved.

7. **scenario round trip / final state**
   - a synthetic scenario starts with or directly applies a status;
   - GDScript and oracle final state/trace expose equivalent stable status state;
   - status numeric modifiers affect a real combat calculation while active.

8. **no implicit lifecycle tick**
   - exercise an ordinary side/activation boundary that CX-009 already supports;
   - verify CX-010 itself does not silently decrement/expire a status merely
     because a round/selection/extra-turn hook was convenient to wire.
   - This is a guard against inventing R13, not a claim about original Eador
     duration timing.

The test suite should clearly separate stable container/stacking cases from
future lifecycle-boundary cases.
