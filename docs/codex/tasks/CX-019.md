# CX-019 — Python oracle scope inventory and guard

Status: `DONE`

Class: `GOVERNANCE_HARDENING`

PYTHON_ORACLE: `NOT_REQUIRED`
Reason: this task changes governance/validation only and must not add or broaden
executable oracle semantics.

## Purpose

Implement the bounded follow-up required by DELIB-0008:

1. create the initial O1–O4 inventory of existing Python oracle modules;
2. make future implementation tasks explicitly declare their Python-oracle scope;
3. add a lightweight validator that prevents silent regrowth of the near-complete
   Python mirror.

This task must not delete, narrow, retire, or behaviorally change any existing
oracle module. It establishes policy metadata and mechanical checks only.

## Accepted policy

DELIB-0008 defines:

- **O1 — permanent independent reference kernels**
- **O2 — curated executable compatibility integration harness**
- **O3 — maintenance-only existing mirror**
- **O4 — vectors/specification/research only**

Future implementation tasks must declare exactly one of:

- `PYTHON_ORACLE: REQUIRED`
- `PYTHON_ORACLE: EXISTING_HARNESS_ONLY`
- `PYTHON_ORACLE: NOT_REQUIRED`

Silence is not permission to mirror.

## Initial inventory

Create one project-owned inventory, preferably:

`docs/ORACLE_SCOPE.csv`

Use a simple, reviewable schema. It must record at least:

- path/module;
- O1/O2/O3/O4 class;
- current role;
- retention criterion or reason;
- whether feature expansion is allowed by default;
- notes/provenance where useful.

Inventory all current **standing oracle Python modules that contain non-test
implementation/reference/tool logic**. Do not count:

- `test_*.py`;
- `conftest.py`;
- caches/generated files;
- package markers with no behavior.

If a utility such as fixture generation is materially part of O1/O4 provenance,
include it explicitly rather than hiding it through a production-only definition.

### Classification calibration

Use DELIB-0008 as authority.

Strong initial O1 candidates include genuinely independent recovered/reference
kernels such as legacy RNG and compact evidence-sensitive arithmetic/parser logic.

The initial O2 compatibility-harness candidates identified during DELIB-0008 include:

- `oracle/scenario.py`

This is an inventory starting point, **not automatic permanent entitlement**.
Classify by actual current load-bearing role.

Again, inspect actual current responsibilities rather than copying this sentence.

O4 is appropriate for vector/spec/research-only utilities that are not standing
parity obligations.

When uncertain between O2 and O3, prefer O3 unless the module is concretely
load-bearing for the retained executable scenario/log compatibility harness.

Do not invent evidence-based O1 status merely because a module contains a recovered
constant somewhere.

## Validator

Add a lightweight project-owned validator, preferably:

`tools/check_oracle_scope.py`

and focused tests for it.

It must perform repository-wide static checks without network access.

### A. Inventory validation

Verify at minimum:

- CSV/schema structure is valid;
- every listed path exists;
- no duplicate paths;
- class is exactly O1/O2/O3/O4;
- required fields are populated;
- expansion/default policy is internally consistent with class;
- every current standing oracle module in the defined inventory scope is classified;
- stale rows for missing modules fail.

Do not try to infer from code whether an implementation is genuinely independent.

### B. Future task declarations

For implementation task files beginning with **CX-019 and later**, require exactly
one valid `PYTHON_ORACLE:` declaration.

Accepted values:

- `REQUIRED`
- `EXISTING_HARNESS_ONLY`
- `NOT_REQUIRED`

For `REQUIRED`, require nearby/structured text naming:

- the retention criterion;
- the exact Python module/kernel/test surface;
- what independent evidence/value it checks.

For `EXISTING_HARNESS_ONLY`, require text making clear that existing O2 coverage must
stay green but the task does not authorize broadening the Python feature surface.

For `NOT_REQUIRED`, require a short reason.

The validator need not rewrite old CX-001..CX-018 task history.

### C. Diff-aware guard

Provide a bounded diff-aware mode so future task runners/reviews can check a task
against its frozen base, for example:

```bash
python3 tools/check_oracle_scope.py \
  --base <frozen-base> \
  --task docs/codex/tasks/CX-XYZ.md
```

The exact CLI may differ if a simpler design is materially better.

In diff-aware mode:

- detect added or modified standing `oracle/*.py` implementation modules;
- `PYTHON_ORACLE: NOT_REQUIRED` must reject such production-oracle expansion;
- `EXISTING_HARNESS_ONLY` may permit only modifications to already-classified O2
  modules needed to keep existing coverage compatible; **new oracle modules must
  fail** under this declaration;
- `REQUIRED` permits the declared exact scope only; modified/added production oracle
  modules outside the declared scope must fail;
- added standing oracle modules must also be added to the O1–O4 inventory.

Do not attempt semantic diff classification. Be conservative and mechanical.

If tests or fixture files under `oracle/test_*.py` change, do not treat that alone as
production-oracle expansion.

### D. Repository integration

Integrate the static validator into an existing governance/hygiene path if there is a
clear small hook. Otherwise document the command and add it to the normal acceptance
gates without building a new framework.

Update future-task guidance/templates so authors see the required field.

13. diff-aware EXISTING_HARNESS_ONLY allows a changed existing O2 module;
14. diff-aware REQUIRED rejects undeclared oracle module expansion;
15. diff-aware REQUIRED allows only its declared scope;
16. oracle test-only changes do not count as production-oracle expansion.

Tests should use temporary synthetic repositories/files where practical rather than
mutating real history.
