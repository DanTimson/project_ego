## Architectural decision

Project EGO must preserve the original/public **action identity and content
mapping** without inheriting the original executable's action-dispatch
architecture.

The long-term boundary is:

```text
source/content action record
    -> canonical ActionDefinition
    -> ActionRecipeResolver
    -> immutable ActionExecutionPlan
         [typed engine-native operations]
    -> shared tactical primitives
```

An action is therefore a player/content-level command. A modified attack is not
a parallel combat engine. It resolves to an ordinary attack operation carrying
ephemeral context.

This tranche establishes that boundary before 0.2.

### Compatibility mapping

The source/import layer may retain original numeric ability IDs and map them to
canonical action identity. Runtime execution must use canonical action identity
and typed plan operations.

Do not:

- reproduce the Genesis dispatcher/jump-table/switch shape;
- branch on Russian display names;
- make binary addresses or offsets runtime identifiers;
- make Scenario contain one bespoke combat implementation per action;
- expose arbitrary legacy opcodes as engine operations.

A clean original-data mapping and clean native architecture are both required.

The accepted public action audit already separates:

1. fourteen explicit unit actions;

Other action shapes inform the architecture but remain non-executable until

## Engine-native action execution plan

### Plan model

Introduce the smallest neutral plan representation that satisfies this tranche.

Conceptually:

```text
ActionExecutionPlan
    operations: ordered immutable list[ActionOp]

ActionOp
    kind
    typed parameters
```

Implement only operation kinds actually exercised by CX-013:

```text
AttackOp
ResourceDeltaOp
```

The plan may be represented by typed classes/resources/dictionaries/enums
consistent with existing repository style. Python/GDScript concepts must match.

The plan is:

- created per command;
- ephemeral;
- not stored on the Combatant;
- not stored back into ActionDefinition;
- independent of display name;
- independent of binary address/offset;
- deterministic from canonical action definition plus action semantics.

An ordered operation list is the composition boundary. Do not build a universal
DSL, arbitrary script interpreter, or one enum entry for every future public
effect family.

### Recipe resolver

`ActionRecipeResolver` (exact name not binding) maps a **canonical action
identity** to an execution plan.

For this tranche:

```text
crushing_blow
    -> [AttackOp(
           mode = melee,
           initiating_attack_scale = 3/2
       )]

shield_bash
    -> [ResourceDeltaOp(
           target = selected enemy,
           resource = stamina,
           amount = -action.magnitude
       )]
```

Known but unsupported actions resolve to an explicit unsupported result before
payment. They must not partially execute generic metadata.

The recipe resolver may read existing semantic metadata such as magnitude,
attack-replacement/scaling/suppression/exclusion fields, but it must not infer a
new behavior merely because a field is nonzero.

### Plan executor

The executor consumes a validated plan and delegates to shared engine
primitives.

It must not contain a second copy of melee damage, death, stamina, or
counterattack logic.

If the plan contains an unsupported internal operation kind, fail loudly as an
internal programming error; do not convert it into a content fallback.

This tranche does not define transactional rollback for future multi-operation
plans. All command/target/availability validation occurs before payment and
execution so the two supported plans are not expected to fail after payment.

## Scenario command boundary

Add or extend one explicit unit-action command with a neutral shape consistent
with current scenario commands, conceptually:

```text
actor + canonical action ID + optional target
```

Required distinctions:

- unknown action;
- known unsupported action;
- actor command/turn refusal;
- actor-side availability refusal;
- missing/illegal target;
- successful plan resolution/execution.

All refusal cases are mutation-free.

Target legality and availability must both be established before payment.
The exact order between those two read-only checks need not mimic Genesis unless
already specified.

Successful resolution:

```text
lookup definition
resolve recipe
validate actor/target
pay exactly once
execute plan
apply CX-009 terminality
```

Do not charge the ordinary melee command again for an attack-replacing action.

## Target legality

Both supported actions require:

- existing target;
- target alive at command entry;
- opposing side;
- adjacent legal melee hex using existing battlefield adjacency.

Shield Bash additionally enforces the action's existing excluded-target metadata,
including incorporeal targets.

Do not create a new target taxonomy merely for this task.

## Payment and terminality

Preserve the existing Action actor-side cost model.

For an attack-replacing action, use the already-existing resolved action cost,
including the existing ordinary-attack surcharge if that is how the current
Action model represents the public cost.

The plan executor must not pay ordinary attack stamina again.

R11 remains binding for the actor's stamina payment: effective modifier `0x12`

CX-009 remains binding:

- successful consuming action spends the actor;
- defender reaction does not spend defender activation;
- refusal does not spend the actor;
- no lifecycle branch refreshes activation.

## AttackOp contract

`AttackOp` is a request to the existing attack/exchange primitive, not an
independent damage implementation.

For CX-013 it needs only the parameters required by Crushing Blow:

```text
mode = MELEE
initiating_attack_scale = exact rational 3/2
```

Use a small immutable/ephemeral attack execution context if necessary.

The context must distinguish initiating primary attack from defender
first-strike/counterattack so the scale cannot leak.

Do not generalize it into a free-form modifier map.

## Crushing Blow — `crushing_blow`

Binding semantics:

- one adjacent living enemy;
- melee attack replacement;
- scale the already-computed effective **initiating melee attack** by exactly
  `3/2`;
- scaling occurs at the settled R10 stage before attack randomisation and
  defence;
- exact integer/truncation semantics;
- never multiply final post-defence damage;
- scale affects only the initiating primary attack;
- defender first strike/counterattack remains ordinary and unscaled when
  otherwise legal;
- ordinary charge/no-retaliation/death gates remain active;
- primary damage reaches the CX-011 sink normally;
- no R17 secondary family is newly implemented;
- no execution context leaks to later commands.

Use a vector where pre-defence attack scaling differs observably from scaling
final damage.

## ResourceDeltaOp contract

`ResourceDeltaOp` delegates a signed resource change to the appropriate tactical
resource primitive/mutation site.

For CX-013 only stamina is implemented.

The stamina operation must preserve R11 by checking effective modifier `0x12`
at this mutation site (or by calling an existing helper that already does so).
Do not create a fictitious universal Combatant setter/interceptor merely for
R11.

A negative stamina result floors at zero.

This operation is an external effect on the target, not actor action-cost
accounting.

## Shield Bash — `shield_bash`

Binding semantics:

- one adjacent living enemy;
- enforce existing excluded-target metadata including incorporeal;
- pay action cost exactly once;
- resolve to one target stamina `ResourceDeltaOp` with
  `amount = -action.magnitude`;
- no ordinary melee damage calculation;
- no life loss;
- no received-damage channel increment;
- no ordinary melee on-hit/secondary chain;
- no first strike;
- no retaliation;
- successful action still obeys CX-009 terminality.

### R11 / modifier `0x12` — resolved

The accepted R11 consumer/write audit establishes a tactical invariant: every
recovered tactical stamina mutation is locally suppressed by effective modifier
`0x12`, including target drains and signed action-effect stamina changes.

Therefore:

```text
if target effective modifier 0x12 != 0:
    Shield Bash target stamina does not change
else:
    target stamina = max(0, target stamina - magnitude)
```

The action itself still resolves successfully after valid targeting/payment; the
target immunity does not turn it into a command refusal.

Add a distinguishing target-`0x12` test.

## Independent review amendment v2 — plan-boundary and bounded exactness correction

**Status remains `REVIEW`.** This is a bounded correction of the existing candidate, not a restart and not permission to widen the action catalogue.

The independent reviewer inspected the complete exported candidate, including all untracked files. The overall source-ID -> canonical Action -> typed plan -> shared primitive direction is provisionally accepted. Crushing Blow/Shield Bash target legality, one-payment intent, primary-context isolation, ordinary death routing, Shield Bash bypass of ordinary damage/reaction, and the explicit unsupported-action boundary are also provisionally accepted.

### R1. Integer-exact scaling, realistic domain

The current `3/2` Crushing Blow scale is float-mediated while documented as exact rational truncation. For legacy-compatible Eador combat this is not a practical precision defect: health, attack and damage are ordinarily O(10), rarely O(100), and below O(1000). Do not add giant-number compatibility tests.

Still, the rule is integer/truncation semantics and integer-only arithmetic is clearer. Replace the new float-mediated ratio with signed integer truncation-toward-zero or equivalent integer-only arithmetic in Python and GDScript. Use realistic odd values such as `1 -> 1`, `3 -> 4`, `9 -> 13`, `19 -> 28`, and retain the existing gameplay vector proving the multiplier occurs before randomisation/defence rather than on final damage. Do not introduce arbitrary numerical caps from this observation.

### R2. Restore resolver / executor / battle-command ownership

Python already has the intended conceptual split: ActionRecipeResolver maps canonical Action to a fresh ActionExecutionPlan; ActionPlanExecutor executes validated plans through injected/shared tactical primitives; Scenario owns command/target validation, payment and battle orchestration.

GDScript currently puts validation, payment, stamina mutation, tracing, plan execution and whole-command execution into `ActionRecipeResolver`. Refactor GDScript to match the frozen architecture conceptually: recipe resolution only creates a fresh plan; a plan executor iterates typed operations; Scenario/battle code owns command-state checks, battlefield target legality, actor availability, one-time payment, orchestration and neutral tracing. Scenario may contain narrow adapters to existing melee/stamina primitives but not bespoke Crushing-Blow/Shield-Bash combat algorithms. Do not add a third runtime file, a generic opcode interpreter, or another story-specific dispatcher.

### R3. Effective 0x12, not raw presence

The GDScript stamina helper must gate Shield Bash by the authoritative effective modifier `0x12` result, not raw `has_modifier_id(0x12)` presence. Preserve an existing `Неутомимый` compatibility alias only insofar as the current effective-modifier architecture already treats it as the same effective rule. Add the strongest distinguishing test the represented model supports.

### R4. Do not leave a falsely generic positive stamina-delta path

CX-013 only executes a negative Shield Bash ResourceDeltaOp. The candidate helper is described as generic signed mutation but only floors at zero. Preferred bounded fix: constrain this CX-013 operation/helper to non-positive drains with an assertion/internal-programming-error guard and document that boundary. If an already-authoritative effective-max-stamina helper exists and makes the accepted upper clamp trivial, reusing it is acceptable. Do not invent new stamina-capacity semantics.

### R5. Remove unused speculative AttackOp policy

Remove `AttackOp.suppresses_counterattack` from Python and GDScript. Neither current recipe needs it; ordinary counterattack suppression remains owned by shared melee exchange.

### R6. Restore GDScript RNG type safety

Restore established `rng: Rng` annotations wherever CX-013 weakened them to `Variant`. The deterministic test RNG already subclasses `Rng`. If a concrete compiler conflict truly requires widening, stop and report the exact call site rather than silently weakening the shared API.

Update architecture/status/formula/matrix/task wording only to corrected implementation truth. ### Independent review R6 resolution — polymorphic RNG seam

The reviewer-requested `Variant -> Rng` tightening was tested and rejected by
the full Godot gate. Genesis scenarios inject `LegacyRng`, which is an
independent `RefCounted` implementation of the project's minimal RNG contract,
not a subclass of native `Rng`. Tightening the shared combat signatures caused:

```text
Invalid type in function 'resolve_exchange'
argument 4 (LegacyRng) is not a subclass of the expected argument class
Scenario._strike -> ScenarioNumericOrdering.resolve_exchange
```

Therefore the shared combat RNG parameters remain `Variant` intentionally so
both native `Rng` and compatibility `LegacyRng` can cross the already-established
composition-root dependency-injection seam. This is not action-specific policy
and does not change RNG selection or rule semantics. Introducing a new common
